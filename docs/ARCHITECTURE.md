# Architecture

A static site. No build step is needed to run it, no server-side logic, no
runtime dependency on anyone else's machine. What you upload is what runs.

```
website/            everything that goes on the webspace
├── index.html      … and 23 more pages, English (the source language)
├── de/             the German mirror, generated by tools/translate.py
├── js/             one module per concern, plain <script>, no bundler
├── css/            tokens · components · app · print + two local hooks
├── data/           rule values, calculator configs, glossary, factions
│   └── units/      ~7300 generated unit files, loaded on demand
├── img/units/      ~4800 unit icons, loaded on demand
├── manifest.webmanifest
└── sw.js           service worker, cache first
```

## The three layers

**Pages** carry the markup and the copy. They pull in the modules they need
with plain `<script src>` tags, in dependency order — there is no module
system and no bundler, so order is the dependency graph. `js/i18n.js` runs in
the `<head>` of every page, before anything else, because it decides whether
this visitor belongs on a different language's copy of the page.

**Modules** are IIFEs that hang one object on `window`: `MechsStorage`,
`MechsCalculator`, `MechsDice`, `MechsShare`, `MechsModifiers`,
`MechsCampaign`, `MechsInitiative`, `MechsMigrate`, `MechsI18n`. They know
nothing about each other beyond that object, and each one guards its
optional partners (`if (window.MechsCampaign) …`), so a page that does not
load a module still works.

**Data** is JSON under `data/`. Rule values are never hard-coded: heat
thresholds, hit location tables, the cluster table, structure by tonnage, the
BV skill factors and both calculator configurations are files. When a new
rulebook lands, this is the folder to edit.

## Where state lives

| What | Where | Key |
|---|---|---|
| Hangar (the 'Mechs you built or imported) | localStorage | `mechs-hangar-<system>` |
| Running battle | localStorage | `mechs-battle-<system>` |
| Campaigns, damage carried over, log | localStorage | `mechs-campaigns-<system>` |
| Paint schemes, painting guide progress | localStorage | `mechs-schemes`, `mechs-guide` |
| Language, theme | localStorage | `mechs-lang`, `mechs-theme` |
| Photos of your models | IndexedDB | one blob per 'Mech id |

`js/storage.js` is the only module that touches storage. Every structure
carries a `version`, and `js/migrate.js` lifts older ones on first read —
it runs once per page view, before any other module gets to look. A
migration is written once and never rewritten: it describes a past that
happened. See `docs/history/MIGRATION-V2.md` for the German-to-English move
and the migration file itself for versions 3 to 5.

A battle keeps a **copy** of each unit's values. Damage in a battle never
touches the hangar entry; only ending a battle can hand damage over to a
campaign, and only the workshop takes it away again.

## The language mechanism

English is the source. `tools/translate.py` writes a mirror per language into
`website/<code>/` and a dictionary into `website/js/i18n-<code>.js`. At
runtime `T("…")` translates the texts a script builds; `Z(name)` puts the
quotation marks of the language around a name. Nothing translated is ever
stored — see `docs/I18N.md`.

## Offline

`sw.js` precaches the app (98 files: pages, scripts, styles, the data files,
the icons) under a version that `tools/build-sw.py` counts up. Unit files and
unit icons are *not* in that list — there are twelve thousand of them. They
land in a second, lasting cache (`mechs-units-v1`) as you look at them, and
that cache survives app updates.

Navigation is network first with a 2.5 second timeout, so a deploy shows up
immediately; everything else is strictly cache first.

## Build and overlay

The repository is neutral: no operator, no imprint, no branding. An instance
adds those in `site/` (git-ignored) and
`python3 tools/opensource/build.py` produces `dist/` from `website/` plus
that overlay — placeholders filled, overlay files copied over. Two CSS files
are empty in the repository and exist to be replaced this way:
`css/tokens.local.css` for the palette and `css/style.local.css` for
everything else about an instance's look.

## Why it looks like this

- **No framework.** The app has to run from a folder on a plain webspace for
  years without anyone re-running a toolchain. Every dependency is a future
  chore.
- **No bundler.** The pages load between two and thirteen small scripts;
  over HTTP/2 that is not the bottleneck, and being able to open one file
  and read it is worth more here than a byte count.
- **Data over code.** Rules change. Code that encodes a rule has to be
  reviewed; a JSON file can be diffed against the book.
