# Languages

English is the source. Every other language is a **pack**: a folder of JSON
files that maps English source text to that language. From a pack,
`tools/translate.py` generates a complete copy of the site under
`website/<code>/` plus a runtime dictionary `website/js/i18n-<code>.js`.

Nothing is translated at runtime that was not translated at build time, and
**nothing translated is ever stored**. What the user sees comes out of
`T()`; what goes into `localStorage` is the English source text.

## Adding a language in five steps

```bash
pip3 install --user beautifulsoup4     # once
```

1. **Register it.** Add an entry to `tools/i18n/languages.json`:

   ```json
   { "code": "fr", "name": "French", "native": "Français" }
   ```

   Exactly one entry carries `"source": true` — that is English, and it
   stays.

2. **Create the folder** `tools/i18n/fr/` with an empty `js.json` (`{}`).

3. **Run the generator.**

   ```bash
   python3 tools/translate.py
   ```

   It writes `website/fr/`, and everything it could not translate lands in
   `tools/i18n/fr/_missing.json`, grouped by page. Missing text stays in
   English — nothing breaks, it just shows.

4. **Work the report off.** Every entry is `"English source": "your
   translation"`. Split them across files however you like; the generator
   reads every `*.json` in the folder except the ones starting with `_`.
   The layout the German pack uses:

   | File | For |
   |---|---|
   | `js.json` | text that scripts build |
   | `common.json` | header, footer, navigation — what is on every page |
   | `pages-*.json` | one file per area (hangar, painting, rules, knowledge) |
   | `data-*.json` | display values out of `website/data/` |
   | `identical.json` | a **list** of texts that stay as they are |
   | `patterns.json` | values that appear in combinations, see below |

5. **Repeat until the report is empty**, then:

   ```bash
   python3 tools/translate.py --check   # exit 1 while anything is open
   python3 tools/build-sw.py --bump     # the new pages into the precache
   ```

## identical.json

Not everything needs translating, and a text that stays the same still has to
be *declared* — otherwise it shows up in the report forever. `identical.json`
is a plain list:

```json
["· TMM", "Fire Control", "AC/20", "2D6"]
```

Abbreviations, unit codes, product names. **Weapon and equipment names are
never translated** — an "ER PPC" is called that at every table in the world.

## patterns.json

Data values are combinatorial: `1/missile`, `2/missile`, `7/14/21 (water
only)`, `Ammo (LRM 20)`. Writing every combination into a dictionary is
hopeless, so a pack may ship patterns:

```json
[
    ["(\\d+)/missile", "$1/Rakete", "g"],
    ["^Ammo \\((.+)\\)$", "Munition ($1)"],
    ["^min \\d+ · [\\d/]+$"]
]
```

`[regex, replacement, flags]` in JavaScript notation. An entry with **only a
regex** means "stays the same in this language" — the pattern version of
`identical.json`. Patterns are tried only when no dictionary entry matches.

One thing to know about patterns: `MechsI18n.back()`, the way from the
display text back to the source, works off the dictionary and cannot invert a
pattern. Where a field is display and input at once — the crit slot editor in
the Classic hangar — the source text of an untouched field is kept as it is,
so a pattern-built name never ends up stored. If you add a pattern for
something that a user can *edit*, think that through.

## What the check run reads

`translate.py --check` collects the strings out of every JS file (including
multi-line calls and concatenations like `"a " + "b"`), the display texts of
the data files, the slot names from `classic-rules.json` and the weapon
values of all unit files. It cannot see text that only exists at runtime — so
every string a script shows has to go through `T("…")`, and quotation marks
around a name through `Z(name)`.

## What the mirror does with links

The generator rewrites relative paths so they resolve from `website/<code>/`,
writes the `alternate` links and the language switch into every page,
including the source pages, and builds a manifest per language. Placeholders
(`{{site.…}}`) are left alone — they are filled by the deploy build, and they
are not paths.

The visitor's choice is remembered in `localStorage` under `mechs-lang` and
respected on the way in; `?query` and `#fragment` travel along, so a shared
link keeps its payload across the language border. Only the home page at the
root falls back to the instance's default language.
